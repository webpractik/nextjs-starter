# Добавление функциональности вертикальным срезом

Используйте это руководство при добавлении пользовательского сценария. Решения закреплены
в [ARCHITECTURE.md](../../ARCHITECTURE.md), их причины и направление импортов описаны
в [обзоре архитектуры](../architecture/overview.md).

Деревья ниже показывают возможный сценарий редактирования товара. Этих файлов нет
в стартере. Текущий Petstore показывает пример API-контракта и не является готовым модулем продукта.

## 1. Определите владельца сценария

Назовите пользовательское действие, входные данные и ожидаемый результат. Для нового
экрана выберите маршрут в `app/`. Если бизнес-возможность уже нужна двум маршрутам,
используйте один модуль `src/modules/<capability>/`.

Перед созданием UI проверьте [карту компонентов](../../COMPONENTS.md) и
[дизайн](../../DESIGN.md). Переиспользуйте публичный UI вместо нового общего компонента.
Локальный UI размещайте в единственной `_components/` маршрута.

Для простого отображения API-ответа вызовите публичный SDK в Server Component или
скомпонуйте Query options с hook в конечном клиентском компоненте. Не создавайте use case,
repository и отдельную доменную модель только для передачи ответа дальше.

## 2. Выделите самостоятельные правила

Если сценарий проверяет инвариант продукта или выполняет несколько шагов, отделите
правила от компонента. Например, domain определяет допустимость изменения товара,
а use case проверяет правило и вызывает переданный порт сохранения. Backend тоже
проверяет свои инварианты и права. Клиентское правило не защищает данные.

Для одного маршрута достаточно соседних файлов без обязательных каталогов слоёв:

```text
app/(public)/products/[productId]/
├── page.tsx                       серверная композиция и чтение
├── actions.ts                     входной адаптер мутации, если он нужен
├── product.ts                     чистые правила и типы продукта
├── save-product.ts                сценарий и его порт сохранения
├── product-api.server.ts          адаптер порта к публичному SDK
└── _components/
    └── product-form.tsx           клиентская форма

tests/unit/app/(public)/products/[productId]/
├── product.unit.test.ts
└── save-product.unit.test.ts

tests/component/app/(public)/products/[productId]/_components/
└── product-form.component.test.tsx
```

Создайте только нужные файлы. `product.ts` и `save-product.ts` не импортируют React,
Next.js, Query, env, logger или SDK. Порт сохранения описывает данные сценария
и его результат. Адаптер импортирует этот порт и `#/api`. Он преобразует DTO только
тогда, когда модель продукта отличается от backend-контракта.

В плоской структуре начинайте `product.ts` с `/** @architecture domain */`.
Файл `save-product.ts` начинайте с `/** @architecture application */`. Маркер стоит до импортов,
директив и других комментариев, чтобы `check:imports` распознал чистый слой.
Если файл находится в каталоге `domain/` или `application/`, слой определяется по пути;
каталог имеет приоритет над маркером. Правильность классификации проверяется при ревью:
скрипт не распознаёт бизнес-правила в непомеченном файле по их содержимому.
Формат маркеров и примеры находятся в [справочнике импортов](../architecture/import-boundaries.md).

## 3. Соберите серверную и клиентскую части

В серверном адаптере используйте `import 'server-only'`, если код читает секреты или
не должен попасть в браузер. Суффикс файла сам по себе не запрещает импорт.
`page.tsx` передаёт клиентской форме только необходимые сериализуемые данные.
Объект порта и обычная серверная функция в props не передаются.

Если выбрана Server Action, `actions.ts` с `'use server'` проверяет входные данные и права
на защищённую операцию. Этот адаптер соединяет use case с SDK-адаптером и возвращает безопасный результат.
Клиент получает ссылку на Server Function по правилам Next.js. Сам use case остаётся
обычной функцией без `'use server'` и принимает зависимости аргументами.

Путь вызовов в этом примере:

```text
форма → Server Action → use case → переданный порт → SDK-адаптер → backend
```

Это последовательность выполнения. В исходниках use case импортирует только чистые
правила и собственные типы. Он не импортирует SDK-адаптер. Не переносите серверную композицию в
клиентский компонент ради короткого вызова.

Server Action не обязательна для каждого запроса. При прямом browser API используйте
публичные `#/api/query` options и обработку ошибок Query. Production browser обращается
к `NEXT_PUBLIC_BACK_URL`. Настройка dev BFF не меняет этот маршрут автоматически.
Серверный SDK использует `BACK_INTERNAL_URL`.

## 4. Обработайте форму, ошибки и кеши

Создайте форму через `useAppForm`, нативный `<form>`, `form.AppField` и `form.AppForm`.
Передавайте Zod напрямую через Standard Schema. Подробный пример находится в
[руководстве по формам](../ui/forms.md).

Верните ожидаемую бизнес-ошибку как типизированный результат и отобразите в форме.
Обработайте ошибку отправки явно. `error.tsx` не перехватывает автоматически
ошибки обработчиков событий и асинхронных мутаций. Не превращайте ошибку API в успешный
пустой ответ и не выводите пользователю секреты из диагностического сообщения.

Определите владельца состояния. Формой управляет TanStack Form, интерактивными данными
API управляет Query, фильтром и страницей в URL управляет nuqs. Локальное состояние
интерфейса остаётся в React state. Не копируйте одни и те же данные в несколько глобальных stores.

После мутации явно обновите затронутый Query cache и серверный кеш, если используются оба.
Cache API находится в адаптере. Выберите механизм инвалидации для вашего контекста Next.js
по [руководству кеширования](../architecture/cache-and-streaming.md).

## 5. Перенесите общую возможность при втором маршруте

Когда тот же сценарий нужен другому маршруту, перенесите его в модуль бизнес-возможности.
Группируйте код по действиям. Не создавайте общие слои для всего приложения:

```text
src/modules/products/
├── index.ts                       универсальные публичные типы и правила
├── server.ts                      серверная композиция и публичные операции
├── client.ts                      клиентские экспорты, если нужны
├── edit-product/
│   ├── save-product.ts
│   └── product-api.server.ts
└── product.ts                     правила, общие для сценариев модуля
```

UI, используемый только одним маршрутом, оставьте в его `_components/`. Если форма
тоже переиспользуется, перенесите её внутрь соответствующего сценария модуля.
Обновите её тесты по зеркальным путям. Stories предусмотрены только для компонентов
в `src/components/`. Не реэкспортируйте серверный адаптер
через универсальный или клиентский index.

Два модуля не импортируют друг друга. Маршрут или layout связывает их
через данные и переданные функции. Domain/application не начинают зависеть от
`src/api/` после переноса; меняется владелец файлов, а не направление зависимостей.
Сохраните маркеры в плоских `product.ts` и `edit-product/save-product.ts`.
Внешние потребители импортируют только корневые `index`, `server` или `client` модуля.

## 6. Проверьте сценарий

1. Проверьте чистые правила и use case в `tests/unit/`. Для IO передайте подставной порт.
2. Проверьте адаптер через существующие schemas, Faker и mock client. Generated код
   меняйте через [API pipeline](api-codegen.md).
3. Проверьте форму в Chromium через `tests/component/`, включая ошибки, фокус и клавиатуру.
4. Для общего компонента в `src/components/` добавьте story в `stories/src/components/`
   с зеркальным путём и тем же базовым именем. Для route-local UI stories не создаются.
5. Выполните `npm run check:imports` для быстрой проверки зависимостей, затем узкие tests
   и `npm run verify:fast`. Последняя команда включает `check:structure`, `check:imports`,
   formatter check, lint и TypeScript; её же вызывает pre-commit.
6. Для нового маршрута выполните свежий `npm run build` и подходящий browser/E2E сценарий.
   Production E2E запускайте отдельно после сборки с `PLAYWRIGHT_SERVER_MODE=standalone`.

Tailwind и существующие tokens используются в первую очередь. CSS Modules допускаются
только в `src/styles/`. Проверка структуры требует тесты
для `src/components/` и `app/**/_components/`, а stories только для `src/components/`.
Наличие проверок у будущих компонентов модулей пока нужно контролировать при ревью.

`check:imports` запрещает framework и SDK imports в распознанных domain/application,
прямые зависимости модулей друг от друга и обход границ через локальные helpers.
При ревью проверьте полноту маркеров и убедитесь, что серверные зависимости не попадают
в клиентский граф: runtime-границы, авторизация и сериализация требуют отдельных проверок.
Точные команды и ограничения проверок приведены в [руководстве тестирования](../testing/testing.md).
