# Доменная модель

## Когда читать

Читайте при создании, изменении или ревью бизнес-понятий, инвариантов и границ
контекстов. Для представления готовых данных без бизнес-правил отдельная
доменная модель не требуется.

## Границы и язык

Начните с существующего словаря, кода, сценариев и архитектурных решений
проекта. Для каждого изменяемого понятия определите смысл, контекст применения,
владельца и потребителей. Новые или противоречивые термины разбирайте через
domain-modeling; в ревью и проектировании сохраняйте режим без записи.

Bounded Context ограничивает область согласованной модели и языка. Папка
функционального модуля, маршрут или endpoint сами по себе контекст не задают.
Один контекст может включать несколько функциональных модулей. Сохраняйте
единственный контекст проекта, пока реальные различия смысла не требуют разделения.

Например, клиент в продажах и плательщик в биллинге могут иметь общий ID, но
разные правила. Не объединяйте их модели только из-за совпадения полей.
Для нескольких контекстов назовите поставщика данных, потребителя и способ
перевода понятий между ними. Внешнюю модель адаптируйте на границе: адаптер
переводит значения, единицы и статусы, сохраняя внутренний язык.

Схема транспортных данных проверяет формат обмена; доменное правило проверяет
смысл. Совпадение формы DTO с моделью не переносит транспортные зависимости
в domain. Эти границы согласуйте с
[правилами импортов](architecture-and-dependencies.md).

## Выбор паттернов

Для каждого вводимого паттерна назовите конкретное правило или потребителя,
которому он нужен. Если их нет, оставьте простой тип и функцию. Классы,
наследование, базовые Entity и универсальные репозитории не обязательны.

| Паттерн | Когда применять | Что подтвердить |
| --- | --- | --- |
| Entity | Объект сохраняет идентичность при изменении свойств | Какие изменения сохраняют идентичность и как сравниваются объекты |
| Value Object | Понятие определяется значением, а не идентичностью | Равенство по значению, неизменяемость, проверку ограничений при создании |
| Aggregate | Несколько объектов должны совместно сохранять инварианты | Корень, состав, границу согласованности и изменение только через корень |
| Domain Service | Бизнес-операция не принадлежит естественно Entity или Value Object | Доменное правило, которое нельзя просто разместить у существующего владельца |
| Repository | Сценарию нужен доступ к агрегатам как к коллекции | Узкий контракт операций над агрегатом и независимость от транспорта и хранилища |
| Domain Event | Уже произошедший доменный факт нужен конкретному потребителю | Момент возникновения, получателя, данные события и последствия обработки |

Value Object, например диапазон дат, создаётся только после проверки своих
ограничений. Ошибку представьте явно; приведение типа само по себе проверкой
значения не является. Изменение создаёт новое значение.

В агрегате не публикуйте изменяемые внутренние объекты в обход корня. Не
объединяйте весь граф связанных данных в агрегат: включайте только то, чему
нужна совместная согласованность. Клиентский агрегат оправдан правилами,
которые клиент действительно может обеспечить.

Domain Service выражает бизнес-решение; HTTP, хранение и последовательность
побочных действий остаются в адаптерах и application. Репозиторий не нужен
для каждого запроса чтения. События не требуют общей шины или Event Sourcing:
при простом взаимодействии достаточно явного вызова через публичный интерфейс.
Границы чтения и команд определены в
[контрактах сценариев](application-contracts.md#чтение-и-команды).

## Инварианты и переходы

Для каждого изменяемого бизнес-правила запишите:

| Правило | Владелец | Разрешённый пример | Контрпример | Способ защиты |
| --- | --- | --- | --- | --- |

Владелец проверяет правило при создании и каждом изменении модели. Обработчик
UI вызывает эту операцию, а не повторяет условие. Ожидаемый отказ сохраняет
инварианты и не оставляет частично изменённый объект.

Сложный жизненный цикл опишите допустимыми переходами и запрещёнными командами.
В TypeScript используйте размеченное объединение состояний или равноценную
модель, если она исключает недопустимые сочетания флагов. Библиотека автоматов
нужна только при оправданной сложности. Переходы бизнес-состояния принадлежат
domain, ход асинхронного сценария — application; подробности см. в
[состояниях процесса](application-contracts.md#состояния-процесса).

## Граница сервера и клиента

Назовите окончательного владельца каждого правила. Проверка в браузере помогает
пользователю, но не подтверждает права, оплату или серверную транзакцию. Сервер
принимает окончательное решение; отказ и конфликт входят в клиентский сценарий.
Не воссоздавайте серверную бизнес-модель целиком ради локального сходства.

Локальные правила и пользовательский ввод могут принадлежать клиенту. Серверные
данные остаются в TanStack Query. Доменное преобразование не создаёт второе
хранилище серверного состояния. Объединение объектов в клиентский агрегат не
делает несколько HTTP-запросов атомарными.

## Проверка и результат

Реализация и рефакторинг должны подтвердить применимые свойства тестами:
идентичность Entity, ограничения и равенство Value Object, инварианты агрегата,
разрешённые и запрещённые переходы. Проверяйте поведение через публичные
операции модели, включая отказ, без React, DOM и реального HTTP.

Передайте границы контекстов, согласованные термины, таблицу правил, выбранные
паттерны с обоснованием и результаты проверок. Для простого чтения достаточно
объяснить отсутствие доменной модели. Неразрешённый смысл правила обозначьте
как открытое решение; не придумывайте его ради завершения реализации.

В ревью не создавайте тесты и документы: используйте существующие доказательства,
а недостающие отмечайте как `needs evidence`. Отсутствие конкретного паттерна
само по себе не является дефектом.
