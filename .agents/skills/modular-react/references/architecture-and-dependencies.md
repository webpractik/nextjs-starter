<a id="неподвижные-инварианты"></a>

## Инварианты

Делите код по функциональности; внутренние слои создавайте под существующие
обязанности. Соблюдайте направление ui → application → domain. Infrastructure
реализует порты application/domain, app связывает реализации.

Границы ограничивают импорты; точки замены — поведение. Предпочитайте небольшой
интерфейс, скрывающий сложную реализацию: передающая вызов обёртка её не скрывает.

<a id="карта-modules"></a>

## Карта модулей

| Модуль | За что отвечает | О чём не знает |
| --- | --- | --- |
| app | Сборка зависимостей, провайдеры, роутер, координация функциональных модулей | Внутреннее устройство функциональных модулей |
| domain | Инварианты, бизнес-правила, доменные значения | React, DOM, Query, транспорт |
| application | Сценарии, порты, координация действий | Конкретные адаптеры |
| infrastructure | API, хранилище, браузерные адаптеры, преобразование DTO и ошибок | Решения представления |
| ui | Модели представления, JSX, доступность, события UI | Бизнес-правила, транспортные DTO |
| shared | Общие примитивы без доменной специфики | Понятия отдельных функциональных модулей |

Повтора в двух модулях недостаточно для переноса в shared: сначала докажите,
что контракт не зависит от предметной области и устойчиво переиспользуется.

## Минимальная структура

```text
src/
├── app/
├── features/
│   └── orders/
│       ├── domain/
│       ├── application/
│       ├── infrastructure/
│       ├── ui/
│       └── public/
└── shared/
```

Не создавайте пустые слои. Простой функциональный модуль может содержать только ui.
Выбор контекста и модели определяется
[бизнес-понятиями и инвариантами](domain-modeling.md), а выделение application —
[контрактом сценария](application-contracts.md#выбор-масштаба).

<a id="публичные-interfaces"></a>

## Публичные интерфейсы

Экспортируйте только нужные имена. `export *` и огромные корневые модули
реэкспорта запрещены. Для крупного модуля создавайте типизированные точки входа
по подпутям:

```typescript
// features/orders/public/order-summary.ts
export { OrderSummary } from '../ui/organisms/OrderSummary'
export type { OrderSummaryProps } from '../ui/organisms/OrderSummary'
```

Потребитель импортирует публичный путь, не зная внутреннего устройства:

```typescript
import { OrderSummary } from '@/features/orders/public/order-summary'
```

## Инверсия зависимостей

Порт объявляется у потребляющего внутреннего слоя: application для сценария,
domain — для доменной возможности, если она нужна модели. Адаптер инфраструктуры
зависит от этого контракта; app выбирает реализацию и передаёт её потребителю.
Передавать можно функцию или объект: DI-контейнер и иерархия классов необязательны.

Проверяйте не только вызовы, но и типы, реэкспорты и обходные пути импортов.
Порт, зависящий от Kubb DTO, React props или QueryClient, сохраняет зависимость
от внешнего слоя даже при использовании `import type`. Результаты и ошибки
порта определяются потребностью внутреннего слоя; транспорт преобразует адаптер.

Доменное правило тестируется без React, DOM и HTTP. Прикладной сценарий
проверяется через публичный вызов с подставными портами. Замена совместимого
адаптера не требует правок бизнес-правил или ветвления по его конкретному типу.
Контрактные проверки описаны в
[контрактах сценариев](application-contracts.md#порты-и-адаптеры), вопросы SOLID —
в [протоколе ревью](critical-review-harness.md#solid).

<a id="atomic-design-как-ui-ось"></a>

## Atomic Design и UI

| Уровень | Назначение |
| --- | --- |
| shared/ui/atoms | Примитивы без доменной специфики |
| shared/ui/molecules | Общие небольшие UI-композиции |
| features/orders/ui/molecules | Небольшие UI-композиции заказов |
| features/orders/ui/organisms | Самостоятельные разделы заказов |
| app/ui/templates | Макет страницы и слоты без конкретных данных |
| app/ui/pages | Сборка страницы маршрута с реальным состоянием |

Импорты направлены page → template → organism → molecule → atom, обратные
запрещены. Atomic Design сохраняет принадлежность модулю. Используйте
существующие UI-примитивы и токены, без пустых каталогов и второй дизайн-системы.

## CSR, SSR и RSC

- Браузерные интеграции находятся в явно выделенном клиентском модуле.
- Серверные модули недоступны из клиентского графа.
- Данные запроса не хранятся в изменяемом состоянии уровня модуля.
- Сборка зависимостей и гидратация следуют правилам фреймворка проекта.

<a id="проверка-boundaries"></a>

## Проверка границ

Используйте существующий ESLint, dependency-cruiser, экспорты пакета или
эквивалентную проверку. Новую зависимость согласуйте до изменения манифеста.
После настройки временно добавьте запрещённый импорт, подтвердите ожидаемый
провал проверки и удалите импорт.

## Контрольный список архитектурного ревью

- [ ] Ответственность однозначна; интерфейс существенно уже реализации,
  скрывает её и позволяет тестировать поведение.
- [ ] Точки замены оправданы адаптерами.
- [ ] Контракты портов принадлежат внутренним слоям; их типы и ошибки не
  протаскивают внешние зависимости.
- [ ] При удалении или замене модуля с сохранением поведения скрытая сложность
  возвращается вызывающему коду. Если она исчезает, модуль лишь передавал
  вызовы. Несвязанные потребители не меняются.
- [ ] Межмодульные импорты публичны; обходов публичных границ и циклов нет.
- [ ] Atomic Design сохраняет принадлежность модулю; серверные и клиентские
  импорты безопасны.
