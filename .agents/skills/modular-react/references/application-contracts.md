## Выбор масштаба

Сценарий описывает цель пользователя и порядок действий для её достижения.
Выделяйте его, когда нужно согласовать бизнес-правила, зависимости, ошибки или
несколько действий. Простая передача запроса не требует отдельного класса,
сервиса или слоя application. Для чистого вычисления достаточно функции domain.

До реализации зафиксируйте контракт существующим способом проекта. Не создавайте
отдельный документ для каждой функции. При ревью восстановите контракт по
вызовам и тестам, неизвестное обозначьте явно.

## Контракт сценария

| Часть | Что определить |
| --- | --- |
| Цель и границы | Наблюдаемый результат, инициатора и владельца сценария |
| Вход | Типы, обязательные данные, источник каждого значения |
| Предусловия | Какие правила проверяются локально, какие подтверждает сервер |
| Результат | Данные успеха и ожидаемые бизнес-отказы без транспортных типов |
| Зависимости | Потребляемые порты и контракт каждого вызова |
| Побочные действия | Порядок, момент подтверждения и последствия частичного успеха |
| Повтор и отмена | Применимость, допустимость повторного вызова, пределы отмены |
| Конкуренция | Поведение при параллельных вызовах, устаревшем ответе и конфликте версии |

Отмену, повтор и конкуренцию уточняйте там, где они возможны; для неприменимого
пункта укажите причину. Продуктовую политику не подменяйте произвольным retry
или перезаписью данных.

Различайте ожидаемый бизнес-отказ, техническую ошибку и дефект программы.
Используйте принятый в проекте тип результата или типизированные ошибки.
Адаптер переводит транспортные статусы в контракт сценария; представление
выбирает сообщение и отображение. Не превращайте любую ошибку в успешное пустое
значение и не добавляйте новую библиотеку результатов без необходимости.

Application вызывает доменные операции и координирует порты. Реализации
передаются извне; случайность, часы и ввод-вывод не должны становиться скрытыми
зависимостями, если влияют на результат. React-хук связывает вызов, события и
статус для UI, сохраняя бизнес-решения внутри сценария и домена.

## Порты и адаптеры

Порт принадлежит потребляющему внутреннему слою и описывает нужную ему
возможность. В его типах и ошибках нет React, Query, Kubb и транспортных DTO.
Конкретный адаптер реализует порт, app передаёт его сценарию. DI-контейнер
необязателен; достаточно параметров или фабрики. Направление импортов и
проверки типов заданы в [архитектурном справочнике](architecture-and-dependencies.md#инверсия-зависимостей).

Подставная реализация порта соблюдает те же предусловия, результаты, ошибки
и побочные действия, что и рабочая. Неподдерживаемый метод не маскируйте
пустым результатом: сузьте контракт потребителя или разделите возможности.
Проверку заменяемости выполняйте общими контрактными тестами применимых
реализаций. Тест адаптера должен достигать его границы; полный мок реализации
этого не доказывает.

## Состояния процесса

Для процесса с несколькими состояниями задайте переходы до реализации.
Следующая таблица показывает возможную политику отправки; конкретные действия
при повторе и конфликте должны следовать требованиям продукта.

| Состояние | Событие | Условие и действие | Следующее состояние |
| --- | --- | --- | --- |
| ready | submit | Вход проверен; начать одну операцию | running |
| running | submit | Если повтор запрещён, не запускать вторую операцию | running |
| running | success | Ответ относится к активной операции | succeeded |
| running | failure | Зафиксирован ожидаемый отказ или техническая ошибка | failed |
| running | version conflict | Сохранить данные для разрешения конфликта | conflict |

Дополните таблицу применимыми отменой, повтором и разрешением конфликта.
Для запрещённого перехода определите явный отказ или игнорирование, для
запоздавшего ответа — правило принятия. При частичном успехе укажите, что уже
подтверждено и как продолжить. Отмена на клиенте не гарантирует откат действия
сервера; безопасный повтор зависит от контракта операции.

Бизнес-состояние принадлежит domain, координация процесса — application,
временные детали UI — представлению. Используйте статус Query для запроса,
если его достаточно; отдельный процесс оправдан собственными переходами,
а не копированием `pending` или `error`.

## Чтение и команды

Чтение без бизнес-поведения может идти через существующую публичную обёртку
TanStack Query к сгенерированной операции. Отдельные сценарий, агрегат и
репозиторий для такого пути не обязательны. Подготовка данных для показа
остаётся в модели представления; доменные правила в неё не переносятся.

Команда со сложными правилами проходит через application и доменные операции.
Адаптер связывает порт с Kubb, а React/Query-обёртка применяет политику кэша по
результату. Domain/application не импортируют QueryClient, хуки или опции Query.
Сгенерированные файлы остаются без ручных правок; существующая граница Kubb сохраняется.

Разделение чтения и команд не требует отдельных баз данных, Event Sourcing
или шины событий. CQRS, Repository и Domain Event вводите по подтверждённой
потребности из [правил доменной модели](domain-modeling.md#выбор-паттернов).
Серверный кэш и его обновление остаются ответственностью tanstack-query;
новый сценарий не создаёт второй источник серверного состояния.

## Проверка и результат

Для выделенного сценария при реализации и рефакторинге проверьте публичный
вызов без React, DOM и реального HTTP: успех, ожидаемый отказ, техническую ошибку
и применимые отмену, повтор, конфликт и частичный успех. Контрактные тесты подтверждают
адаптеры отдельно. В UI проверьте соответствие результата и доступных действий,
включая запрет повторной команды, если он задан продуктом.

Передайте контракт, таблицу переходов при её необходимости, места подключения
адаптеров и результаты проверок. В ревью используйте только существующие тесты
и команды без записи; недоказанные свойства отмечайте `needs evidence`.
Неясное правило остановите на уровне соответствующего решения, сохранив
возможность продолжить независимую часть задачи.

## Источник

Направление зависимостей и разделение сценариев и адаптеров:
[Robert C. Martin, The Clean Architecture](https://blog.cleancoder.com/uncle-bob/2012/08/13/the-clean-architecture.html).
Контракты асинхронных процессов и интеграция с Query выше задают правила пакета.
