## Выбор режима

- Создание функциональности: пользователь просит добавить или расширить поведение.
- Проектирование: определить интерфейсы, ответственность и точки замены без
  правок до отдельного запроса реализации.
- Рефакторинг: изменить структуру, сохранив поведение.
- Ревью выбранных модулей и инвариантов: проверять без записи.
- Обзор всего проекта: попросить пользователя явно вызвать
  improve-codebase-architecture.

<a id="маршрутизация-required-sub-skill"></a>

## Подключение обязательных скиллов

| Скилл | Когда применять |
| --- | --- |
| codebase-design | Любое проектирование, рефакторинг или ревью архитектуры |
| domain-modeling | Введение или изменение доменных терминов, инвариантов или границ контекста; при ревью противоречивой модели — только диагностика |
| vercel-react-best-practices | Создание, изменение или ревью React-кода |
| typescript-magician | Контракты TypeScript, any/unknown, ошибки типов, tsc |
| incremental-implementation | Реализация или рефакторинг нескольких файлов либо изменение, вышедшее за рамки минимального |
| code-simplification | После успешных проверок реализации или рефакторинга |
| doubt-driven-development | Высокий риск, спорное или противоречивое замечание, дорогое решение между модулями |
| improve-codebase-architecture | Обзор всего проекта, только по явному вызову пользователя |
| tanstack-query | Подробная работа с загрузкой данных, включая ключи, кэш, мутации, пагинацию и гидратацию Query |
| openapi | Создание или изменение границы HTTP API, операции либо контракта обмена; до генерации Kubb |

Читайте актуальные SKILL.md, не заменяя их пересказом. Сохраняйте границы задачи:
при ревью и проектировании разрешена только диагностика, без правок файлов,
тестов и Git. Коммит и отправка в remote требуют явного запроса; без него
шаг коммита `incremental-implementation` служит контрольной точкой.

После SKILL.md vercel-react-best-practices читайте только нужные правила.
code-simplification может завершиться без правок; посторонняя чистка запрещена.
Изменённые доменные термины и инварианты сверяйте с кодом и документацией,
неразрешённые расхождения уточняйте.

Объясните пользователю, что disable-model-invocation: true у
improve-codebase-architecture требует его явного вызова. Подробные решения по
загрузке данных оставьте tanstack-query. Передавайте doubt-driven-development
материал, контракт и границы задачи без исходного вывода; его гипотезы тоже
требуют подтверждения.

<a id="правила-разрешения-конфликтов"></a>

## Разрешение конфликтов

Соблюдайте приоритеты и определения из SKILL.md. Узкие публичные точки входа
допустимы, огромные модули реэкспорта запрещены. Сложные типы оправдывайте
безопасностью типов, затем упрощайте.

<a id="процесс-для-новой-feature"></a>

## Создание функциональности

1. Изучите правила, команды, граф модулей и среду проекта. Для HTTP API найдите
   точки входа OpenAPI/Kubb и переменные окружения; в отчёте указывайте только роли.
2. Загрузите обязательные скиллы.
3. Свяжите изменяемые доменные термины и инварианты с кодом и документацией;
   расхождения уточните до реализации. По [доменной модели](domain-modeling.md)
   определите контекст, владельцев правил и минимально нужные паттерны.
4. Для HTTP API проверьте контракт через openapi, выделите сгенерированный код
   и серверную и клиентскую сборки зависимостей. Контракт меняйте только при
   доказанном изменении или несоответствии формата обмена.
5. Определите публичный интерфейс, владельцев состояния, точки замены и адаптеры.
   Если выделен сценарий, зафиксируйте [его контракт](application-contracts.md)
   и применимые ошибки, повтор, отмену и конфликты до реализации.
6. Многофайловое или неминимальное изменение выполняйте сквозными срезами через
   incremental-implementation, минимальную правку одного файла — напрямую.
7. Для HTTP API пройдите дополнительные критерии готовности ниже: сначала
   генерация, типы и повторная генерация, затем изоляция и тесты выполнения.
8. Для TypeScript запустите совместимый `tsc --noEmit` до и после изменения,
   затем форматирование, линтер, типы, тесты и сборку текущего среза.
9. Проверьте Vercel, архитектуру, Effects, декомпозицию и Atomic Design.
   Для модели и сценария пройдите проверки соответствующих справочников;
   примените [вопросы SOLID](critical-review-harness.md#solid) к изменённым модулям.
10. После успешных проверок примените code-simplification к изменённому коду.

<a id="процесс-structural-design"></a>

## Проектирование

Изучите граф модулей, правила, среду и границы задачи. Определите интерфейсы,
владельцев состояния, точки замены и направление зависимостей. Передайте
решение, допущения, открытые вопросы и способ проверки. Для бизнес-логики
добавьте контекст и инварианты, для выделенного сценария — контракт и переходы.
Скиллы применяйте только для диагностики, без правок файлов, тестов,
зависимостей и Git. Реализация требует отдельного запроса.

<a id="процесс-рефакторинга"></a>

## Рефакторинг

1. Закрепите поведение характеризующими тестами; для TypeScript сохраните
   исходный результат совместимого `tsc --noEmit`.
2. Составьте карту модулей, интерфейсов и точек замены. Выберите одну причину
   изменения. Для бизнес-логики восстановите контекст и инварианты по
   [справочнику модели](domain-modeling.md), для выделенного сценария —
   [его контракт](application-contracts.md). Перенос кода не меняет эти правила.
3. Через incremental-implementation переносите по одной обязанности. Минимальный
   рефакторинг одного файла выполняйте напрямую.
4. На каждом шаге сохраняйте сборку и поведение.
5. Проверяйте контракты TypeScript, правила React и SOLID. Подтвердите применимые
   инварианты, переходы и контракты портов проверками из справочников модели
   и сценариев.
6. Для HTTP API пройдите дополнительные критерии готовности ниже.
7. Для TypeScript повторите совместимый `tsc --noEmit`. После успешных проверок
   упрощайте только изменённый код.
8. Не смешивайте изменение поведения, дизайн и постороннюю чистку.

Полная одномоментная переработка не является допустимым решением по умолчанию.

<a id="процесс-focused-review"></a>

## Ревью выбранных модулей

Без явного запроса исправлений работайте только в режиме диагностики.
Применяйте скиллы по таблице выше. Для HTTP API изучайте существующие
конфигурации, сгенерированные файлы и сборку зависимостей без генерации и команд
записи. Непроверенные генерацию и отсутствие расхождений отмечайте `needs evidence`.

Прочитайте `critical-review-harness.md` и выполните его протокол: определите
границы и охват, проследите зависимости до потребителей, проверьте гипотезы
контрпримерами, опубликуйте только подтверждённое. Перенесите `needs evidence`
в ограничения. При высоком риске или спорном выводе выполните
независимую перепроверку и подтвердите её гипотезы. Соблюдайте формат отчёта,
включая случай без замечаний; чек-лист не заменяет чтение кода и работающие
проверки.

<a id="проверки-по-layers"></a>

## Проверки по слоям

| Слой | Проверка |
| --- | --- |
| domain | Чистые тесты применимых инвариантов, идентичности, равенства и переходов через публичные операции |
| application | Контракты сценариев через порты: успех, отказ и применимые повтор, отмена, конфликт и частичный успех |
| infrastructure | Контрактные и интеграционные тесты; общие проверки совместимых реализаций порта |
| ui | Наблюдаемое поведение, доступность и взаимодействия |
| atoms/molecules | Stories и тесты отдельных компонентов |
| organisms | Компонентные и интеграционные тесты, без Stories |
| templates | Тесты структуры и раскладки, без Stories |
| pages | Интеграционные и E2E-тесты, без Stories |
| SSR/RSC | Гидратация и проверка серверных и клиентских импортов |
| Генерация API | Выходы Kubb 5 для TypeScript, Zod 4, встроенного Fetch и React Query; проверка типов; повторная генерация без расхождений |
| Архитектура | Публичные импорты, циклы и тест отклонения запрещённой зависимости |

## Обработка проблем

- Докажите, какие ошибки существовали раньше и не связаны с изменением.
  Ошибки вне задачи не блокируют её завершение; сообщайте их отдельно.
- Недостающие средства проверки архитектуры предложите в минимальном составе;
  новую зависимость согласуйте до добавления.
- Неясное поведение закрепите характеризующим тестом до переноса кода.
- Для Effect назовите внешнюю систему, контракт синхронизации и необходимость
  очистки операций и ресурсов.
- Назовите недоступный обязательный скилл, не заявляя о его запуске.
- Неясный граф сначала опишите по реальным зависимостям, без навязывания шаблона.
- Для спорного владельца бизнес-правила выясните, должно ли правило работать
  без React, и назовите принимающий решение модуль.
- Сохраняйте более строгие правила проекта; их изменение оформляйте отдельно.

<a id="handoff"></a>

## Передача результата

После реализации перечислите изменённые модули и интерфейсы, направление
зависимостей, решения по декомпозиции и Effects, команды, результаты и ограничения.
Для бизнес-логики приложите границы модели, инварианты и обоснование паттернов;
для сценария — контракт, переходы при необходимости и проверки заменяемости.

Ревью оформляйте по протоколу критического ревью и критериям ниже: замечания по
серьёзности, охват, `needs evidence`, итог. При отсутствии замечаний всё равно
назовите проверенные файлы, зависимости, состояние, Effects, режимы выполнения
и команды, не заявляя полное соблюдение требований.

После проектирования передайте интерфейсы, владельцев состояния, точки замены,
направление зависимостей, допущения и способ проверки. Во всех отчётах отделяйте
ранее существовавшие ошибки и ошибки вне задачи.

<a id="ограничение-этой-версии-skill"></a>

## Ограничение версии скилла

Не создавайте оценочные прогоны агента, бенчмарки и фикстуры для них. Под тестами
здесь понимаются проверки целевого проекта. Статическая проверка скилла не
доказывает качество его поведения.

<a id="definition-of-done-для-implementation-и-refactor"></a>

## Готовность реализации и рефакторинга

Проверяйте изменённые или входящие в задачу файлы, модули и зависимости.
Полный охват требует явного согласования; ошибки вне задачи фиксируйте
с доказательствами, не блокируя завершение.

- [ ] Обязательные скиллы выполнены.
- [ ] Для изменяемой бизнес-логики названы контекст, владельцы и инварианты;
  DDD-паттерны оправданы. При отсутствии такой логики указана неприменимость.
- [ ] Для выделенных сценариев подтверждены входы, результаты, ошибки и
  применимые переходы, повтор, отмена и конкуренция. Простому чтению не добавлены
  лишние слои или второй серверный кэш.
- [ ] Применимые вопросы SOLID проверены; модели, сценарии и адаптеры прошли
  проверки своих контрактов. Непроверенное свойство не выдано за успешную проверку.
- [ ] Рабочие файлы компонентов не превышают 800 строк; свыше 200 строк проведён
  разбор декомпозиции. Каждый рабочий файл объявляет один React-компонент.
- [ ] Atomic Design сохраняет принадлежность модулю; Stories есть только
  у атомов и молекул.
- [ ] Нет обходов публичных границ и циклов. Domain/application не зависят от React
  и конкретной infrastructure; представление не принимает бизнес-решений.
- [ ] Effects прошли лестницу решений и очищают созданные ресурсы и отменяемые
  операции. Состояние TanStack Query не дублируется.

Для HTTP API в границах задачи дополнительно проверьте:

- [ ] Исходный OpenAPI-контракт служит единственным входом Kubb; включены
  TypeScript, Zod 4, встроенный Fetch с валидацией и хуки React Query.
- [ ] Сгенерированные файлы не редактируются; UI использует их только через
  рукописную публичную границу своего модуля. Domain/application не зависят от
  конкретного транспорта.
- [ ] Генерация Kubb, проверка типов и повторная генерация без расхождений прошли.
- [ ] Серверная и клиентская сборки зависимостей используют разные найденные
  переменные окружения без взаимной подмены. Серверный модуль недоступен из
  клиентского графа.
- [ ] Отдельный серверный клиент каждого запроса и стабильный браузерный клиент
  передаются в запросы через типизированную конфигурацию Kubb. Тесты с
  искусственными данными доказывают оба пути базового URL и немедленный отказ
  с указанием только роли, без реального API, имён и значений переменных.

Для всех задач реализации и рефакторинга:

- [ ] Внешнее хранилище подключено через useSyncExternalStore.
- [ ] Существующие проверки форматирования, линтера, типов, тестов и сборки
  выполнены без новых ошибок.
- [ ] Доказано, какие ошибки существовали до изменения.

<a id="definition-of-done-для-review-и-design"></a>

## Готовность ревью и проектирования

- [ ] Границы и проверенные зависимости названы. Обязательные скиллы применены
  только для диагностики; без отдельного запроса исправлений или реализации
  файлы, тесты, зависимости и Git не менялись.
- [ ] Каждое направление отмечено `checked`, `not applicable` с причиной либо
  `needs evidence` с точным ограничением.
- [ ] У замечаний есть серьёзность, место, инвариант, доказательство, последствие,
  проверенный контрпример и минимальное исправление. Отклонённые гипотезы
  исключены; `needs evidence` не выдан за дефект или успешную проверку.
- [ ] Высокий риск и спорные выводы прошли doubt-driven-development и повторное
  подтверждение, когда это требовалось.
- [ ] Отчёт без замечаний перечисляет проверки и ограничения. Ранее
  существовавшие ошибки и ошибки вне задачи отделены от текущих.
- [ ] Проектное решение фиксирует интерфейсы, владельцев состояния, точки замены
  и допущения. Замечания не блокируют ревью; итог не заявляет полное соблюдение
  целевых требований.
- [ ] Для HTTP API названы владельцы OpenAPI/Kubb, граница сгенерированного кода,
  изоляция серверных и клиентских переменных и непроверенные расхождения.
