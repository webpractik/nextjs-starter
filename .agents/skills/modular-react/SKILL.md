# Модульная архитектура React + TypeScript

## Основной принцип

Делите код по функциональности, ограничивая интерфейсы и направление
зависимостей. Atomic Design классифицирует UI внутри модулей. Представление
получает готовые данные; бизнес-решения принимают domain/application.

Выбирайте DDD-паттерны под конкретные правила. Контракты сценариев определяют
поведение, а SOLID проверяет ответственность и заменяемость модулей. Простое
чтение данных не требует агрегата, репозитория или отдельного сценария.

## Совместимость

Требуются React, TypeScript и скиллы по архитектуре, React и TypeScript.
Используются TanStack Query, Kubb, Zod, react-use и useSyncExternalStore.

## Обязательные требования

- Зависимости направлены ui → application → domain. Infrastructure реализует
  порты, app связывает реализации.
- Между функциональными модулями разрешены только узкие публичные точки входа
  или подпути. Импорты внутренних файлов, циклы, огромные модули реэкспорта и
  пустые слои «на будущее» запрещены.
- Файл рабочего React-компонента длиннее 200 строк требует разбора декомпозиции;
  больше 800 строк — запрещён. Тесты, Stories, фикстуры и сгенерированный код
  исключены.
- Один рабочий компонент занимает один файл. Вложенные компоненты запрещены.
- Stories создаются только для атомов и молекул.
- Серверным состоянием владеет TanStack Query.
- Kubb генерирует HTTP API с обязательными `@kubb/plugin-ts`,
  `@kubb/plugin-zod`, `@kubb/plugin-fetch` и `@kubb/plugin-react-query`.
- `@kubb/plugin-fetch` использует встроенный `globalThis.fetch`. Axios и ручные
  дубликаты сгенерированного транспорта, типов, схем и хуков запрещены.
- Fetch-плагин включает `validator: "zod"`, React Query — `client: "fetch"` и
  `hooks: true`.
- Ядро и плагины используют совместимые версии Kubb 5; сгенерированный код —
  `zod@4` и `@tanstack/react-query@5`. Переход с предыдущих основных версий
  требует отдельной миграции.
- Общее клиентское состояние внешнего менеджера подключается через
  useSyncExternalStore. react-use допустим только для вспомогательных хуков.
- Effect синхронизирует внешнюю систему. Представление и хук-контроллер не
  принимают бизнес-решений.
- Изменяемые бизнес-правила имеют владельца, инварианты и контрпримеры.
  Выбранные DDD-паттерны обоснованы; окончательные серверные решения не
  подменяются проверкой в браузере.
- Выделенный сценарий имеет контракт входа, результата, ошибок и побочных
  действий. Порты принадлежат внутреннему слою; применимые повтор, отмена
  и конкуренция определены до реализации.
- При ревью выбранных модулей обязательны проверка охвата, поиск нарушений,
  попытка их опровергнуть и подтверждение каждого замечания.

## Подключение скиллов

Выбирайте обязательные скиллы по таблице в справочнике рабочих процессов.
Для обзора всего проекта нужен явный вызов improve-codebase-architecture.

Перед действием читайте актуальные SKILL.md применимых скиллов, сохраняя
полномочия задачи. Запрос реализации или рефакторинга HTTP API включает
обязательные зависимости Kubb после фиксации в плане изменений. Ревью и
проектирование запрещают правки кода и зависимостей; коммит и отправка в remote
требуют отдельного явного запроса.

## Выберите режим

- Создание функциональности или проектирование без изменений файлов.
- Рефакторинг с сохранением поведения.
- Ревью архитектуры выбранных модулей без изменений файлов.
- Обзор всего проекта по явному вызову improve-codebase-architecture.

Визуальная правка, стилизация и загрузка данных без архитектурной задачи
исключены. Сохраняйте роутер, фреймворк, сборщик и единую дизайн-систему.

## Граница Kubb и сборка зависимостей

Выделите сгенерированный код Kubb в infrastructure/API и не редактируйте его.
Domain не импортирует транспортные DTO, схемы Zod и хуки React Query. Если DTO
и доменная модель различаются, преобразуйте их рукописным адаптером.
Представление получает готовый интерфейс API через рукописную публичную точку
входа своего модуля. Только она импортирует сгенерированные опции и хуки React
Query; прямые импорты внутренних файлов из UI запрещены.

Настраивайте базовые URL вне сгенерированных файлов, в двух отдельных модулях:
серверный читает серверную переменную окружения проекта, клиентский — отдельную
публичную. Сначала найдите их реальные имена и правила публикации фреймворка.
Если переменных нет или разделение не доказано, остановитесь до записи и
запросите решение. Не придумывайте имена и не выводите имена или значения в
отчёт. Серверный модуль недоступен из браузерного графа импортов.

Переменные не подменяют друг друга. При пустом значении немедленно завершайте
операцию с ошибкой, указывающей только роль (`server base
URL`/`client base URL`), без имени и значения переменной. Сервер создаёт отдельный
сгенерированный клиент через `createClient` для каждого запроса; браузер
использует один стабильный экземпляр. Публичная обёртка модуля передаёт клиент
сгенерированным запросам и мутациям через фактический типизированный параметр
конфигурации Kubb v5. Глобальный `setConfig` на сервере запрещён.

Оба модуля используют единый сгенерированный контракт операций и ключей. Пока
семантическая эквивалентность серверных и браузерных endpoints не доказана,
гидратация SSR заблокирована.

`openapi` отвечает за исходный контракт, Kubb — за сгенерированные Fetch, типы,
Zod и React Query, `tanstack-query` — за семантику кэша. Этот скилл отвечает за
границы модулей, сборку зависимостей и проверки генерации и расхождений средствами
проекта. Для HTTP API один раз прочитайте актуальные `SKILL.md` этого скилла и
применимых `openapi`/`tanstack-query`; совместите их требования к Kubb без
рекурсивных вызовов.

## Рабочий процесс

1. Определите режим, границы задачи, правила репозитория, среду, команды и граф
   модулей. Загрузите применимые скиллы и справочники.
2. Назначьте ответственность, публичные интерфейсы, владельцев состояния и
   точки замены поведения. Для бизнес-логики определите контекст, инварианты
   и необходимый масштаб модели; для сценария — его контракт.
3. Следуйте `workflows-and-verification.md`; требования Kubb применяйте только
   к HTTP API в задаче.
4. При ревью и проектировании изучайте конфигурации и сгенерированные файлы без
   записи и запуска генерации. Непроверенные генерацию и отсутствие расхождений
   отмечайте `needs evidence`.
5. Сообщите доказательства, исключения и ранее существовавшие ошибки.

## Приоритет правил

Явные требования пользователя → более строгие правила проекта → этот скилл →
совместимые правила подключённых скиллов. TanStack Query приоритетнее советов
для SWR. Граница зависимостей ограничивает импорты, точка замены — поведение.

## Критерий завершения

Реализацию и рефакторинг завершайте по
[их критериям готовности](references/workflows-and-verification.md#definition-of-done-для-implementation-и-refactor).
Для ревью и проектирования действуют
[отдельные критерии](references/workflows-and-verification.md#definition-of-done-для-review-и-design):
найденные нарушения не мешают завершить ревью. Без оценочных прогонов не
заявляйте, что поведение скилла прошло бенчмарк.
