# Сопоставление с проектом и реализация

На `G3` исследуй проект, зафиксируй модель экрана, адаптивные выводы, повторное использование и выбор значений. На `G4` создай `implementation-manifest.json`. Источники разобраны в [`source-and-assets.md`](./source-and-assets.md).

## Исследование проекта

До изменений найди владельца маршрута, границы модулей, точки входа React, настройки Tailwind, токены, контрольные ширины, шрифты, ресурсы, компоненты, варианты, команды проекта, браузерные проверки и файл воспроизводимых данных.

Для каждой части интерфейса изучи подходящие компоненты. Запиши путь, API, варианты, семантику DOM, способ композиции и конкретную причину отказа. Название компонента не доказывает его пригодность.

Заполни [`pre-code-evidence.md`](../templates/pre-code-evidence.md) до изменения кода, стилей, данных и ресурсов приложения. Отделяй факты проекта от наблюдений Figma и допущений.

## Шрифты

Для каждого семейства из Figma сначала проверь локальные файлы, пакеты и токены проекта. Если точного семейства нет, найди пакет `@fontsource/<font-id>` и проверь нужные начертания и веса. Запиши запрос, пакет и разрешённую версию либо подтверждённое отсутствие.

Устанавливай пакет после `G3` только менеджером пакетов проекта и только если зависимость входит в проверенный контракт. Не подменяй отсутствующий шрифт без согласования.

## Модель экрана

В документе со сведениями до начала реализации сохрани эти заголовки и порядок:

1. `Модель компоновки`
2. `Повторно используемые компоненты`
3. `Новые компоненты`
4. `Токены`

`Модель компоновки` описывает нормальный поток, Flex или Grid, порядок содержимого, размеры и вертикальный ритм. `Повторно используемые компоненты` перечисляют проверенные компоненты проекта. `Новые компоненты` объясняют новые границы и причины отказа от кандидатов. `Токены` ссылаются на порядок выбора значений.

До закрытия `G3` обновляй документ при каждом новом подтверждении. После `G3` не меняй его: новые сведения укажи в итоговом отчёте. Если после `G4` они требуют правки реализации, выполни переход `implementation-changed`.

## Адаптивные выводы

Раздел `Адаптивные выводы` содержит строку для каждой записи `$.viewports`. Для переходов используй литералы `fluid`, `fixed`, `wrap`, `reordered`, `scrollable` либо точное русское описание смены направления, видимости или приоритета содержимого.

Помечай вывод как `observed`, `inferred` или `unknown` и указывай источник. Сохраняй одно дерево содержимого и DOM. Сначала используй контрольные ширины проекта. Новую ширину вводи только для подтверждённого перехода, который нельзя выразить существующей системой; одна ширина макета сама по себе этого не доказывает.

## Повторное использование

Правильная семантика HTML важнее повторного использования. Совместимый компонент проекта важнее нового примитива для одной задачи. Для нового компонента перечисли изученных кандидатов и точные несовместимости.

Не меняй общую архитектуру, глобальные стили, стратегию зависимостей или несвязанные маршруты ради удобства. Если использование общего компонента нарушает обязательное правило, примени `STOP` и запроси согласование изменения этого компонента.

## Порядок выбора значений

Выбирай каждое значение на первой допустимой ступени:

1. Существующий React-компонент.
2. Существующий семантический токен.
3. Существующий примитивный токен.
4. Значение шкалы Tailwind.
5. Новый токен с обоснованием.
6. Произвольное значение, если подтверждено, что оно должно быть уникальным.

Записывай, почему предыдущая ступень не подошла. Даже если так результат будет ближе к макету, нельзя пропускать подходящий компонент или токен.

## Вертикальный ритм

Расстояние между вертикальными соседями задавай через `gap` контейнера или `margin-bottom` и `mb-*` предыдущего элемента. Внутри корня реализации не используй `margin-top`, `margin-block-start`, `mt-*`, `my-*`, `m-*` и вертикальные сокращения `margin` или `margin-block`. Горизонтальные отступы разрешены.

Если расстояние нужно над элементом, задай его у предыдущего соседа или контейнера. Если общий примитив несовместим с этим правилом, примени `STOP`; не обходи ограничение скрытой подгонкой.

## Запрещённые обходы

1. Основная компоновка через `position: absolute` или `fixed`. Исключение допустимо для подтверждённого слоя поверх содержимого или декора.
2. Высота, обрезка, `overflow: hidden` или ограничение строк, которое мешает длинному содержимому расти.
3. Исходник или визуальное подтверждение, вставленное вместо интерфейса.
4. Новый примитив без записанного поиска компонентов проекта.
5. Подгонка через `transform`, `scale`, `translate`, `zoom` или компенсацию контрольной ширины.
6. Обычные элементы управления, текст, карточки, списки, таблицы, формы или компоновка через Canvas. Исключение должно быть явно включено в контракт.
7. Скрытие элемента через `display`, `visibility`, `opacity`, нулевой размер, маску или вынос за экран без подтверждённого состояния.
8. Отдельные деревья настольной и мобильной версий ради попиксельной подгонки.

Также не используй `iframe`, сырой HTML и `dangerouslySetInnerHTML` для воспроизведения дизайна.

## Манифест реализации и implementationHash

На `G1` запиши в `baseline.revision` полный хеш коммита `HEAD`. Профиль `git-visible-v1` рассматривает все отслеживаемые изменения относительно этого коммита и новые неигнорируемые файлы. Для каждой уже существующей правки запиши в `baseline.preExistingChanges` путь, `kind`, режим Git и SHA-256 текущих байтов; для ранее удалённого файла режим и хеш равны `null`. Список сортируется по пути. Эти правки не входят в реализацию и до `G8` должны остаться побайтно неизменными.

После внесения изменений на `G4` создай `artifacts/visual/<task-id>/implementation-manifest.json` по [шаблону](../templates/implementation-manifest.json). Это текущий указатель на реализацию. `files` должен точно совпасть со всеми изменениями, видимыми профилю `git-visible-v1`, за вычетом записей из `baseline.preExistingChanges`: кодом, стилями, ресурсами приложения, воспроизводимыми данными, настройками зависимостей, файлом блокировки и удалениями. Каждый путь обязан лежать в одном из `allowedImplementationRoots` либо точно совпадать с `data.fixture` или согласованным файлом устанавливаемой зависимости. Обязательно включи существующий целевой модуль или файл внутри него и точный `data.fixture` из задачи. Для согласованной установки используй ровно `packageJsonPath`, `lockfilePath` и `specifier` из контракта; оба файла входят в манифест как `kind: "file"`. Не включай сам манифест, каталог подтверждений задачи, её тестовые эталоны, `node_modules` и `.git`.

Сортируй записи по `path`, лексикографически сравнивая его байты UTF-8. Для обычного файла укажи `kind: "file"`, режим `100644` или `100755` и SHA-256 его байтов. Для удаления используй `kind: "deleted"`, `mode: null` и `hash: null`. Символические ссылки, подмодули, специальные файлы, конфликтующий индекс, `assume-unchanged` и `skip-worktree` не поддерживаются и приводят к `STOP`. Корнем проверки должен быть корень репозитория. `HEAD` должен оставаться равным `baseline.revision`.

В `taskContractHash` запиши SHA-256 точных байтов канонического `task-contract.json`. Для `rootHash` сначала добавь строку `task + NUL + taskContractHash + LF`, затем для каждого файла — `path + NUL + kind + NUL + mode-or-null + NUL + hash-or-null + LF`. Вычисли SHA-256 всех UTF-8 байтов и добавь префикс `sha256:`. Этот `rootHash` является `implementationHash`.

Значение `<implementation-id>` состоит из 64 шестнадцатеричных знаков после `sha256:`. Сохрани побайтно равную копию манифеста в `artifacts/visual/<task-id>/implementations/<implementation-id>/implementation-manifest.json`. Корневой файл можно заменить при новой реализации, а версионированную копию нельзя менять.

После любой следующей правки до `G8` пересчитай хеши, создай новый каталог версии и выполни переход `implementation-changed` из [`gates.md`](./gates.md#события-журнала-и-смена-состояния). Старый каталог сохраняет историю `G4`-`G7`.

Проверка не обнаруживает новые файлы, которые Git считает игнорируемыми, не устанавливает автора изменений и не гарантирует, что перечислены все файлы, влияющие на отрисовку. После `G1` она также не может отличить внешнее изменение от работы агента. Игнорируемый файл нельзя использовать как часть воспроизводимой реализации. Если внешнее изменение выходит за согласованную область, примени `STOP`; иначе оно должно попасть в манифест.
