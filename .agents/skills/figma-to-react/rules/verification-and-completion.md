## Контракт захвата и полная матрица

Создай `capture-contract.json` по [шаблону](../templates/capture-contract.json). Каждый случай фиксирует идентичность Figma, маршрут, область, размер и DPR, состояние, данные, локаль, часовой пояс, параметры отображения, среду, готовность, селекторы и один `evidenceMode`. Все случаи используют один отпечаток среды: одинаковые браузер, ОС, контейнер, режим `headless` и набор хешей шрифтов.

Для каждой записи `$.states` со значением `applicability: "required"` создай хотя бы один случай с каждой записью `$.viewports`. Это полное декартово произведение обязательных состояний и областей просмотра. Хотя бы одно состояние должно быть обязательным. Состояние `not-applicable` не входит в матрицу, не используется в случаях захвата и сохраняет непустое `evidence` в контракте задачи.

Режимы имеют разный состав:

- `visual-reference`: обязательна хотя бы одна запись; объект `reference`, `evidencePath: null`, эталон и визуальные итерации.
- `behavior-only`: добавляется, только когда `evidenceModes.behaviorOnly.applicability` равно `required`; содержит `reference: null` и канонический `evidencePath` к `evidence.json`.
- `responsive-only`: подчиняется `evidenceModes.responsiveOnly` и тем же ограничениям, но утверждения относятся к адаптивному поведению.

Для неприменимого режима в задаче укажи непустое объяснение, а случаи этого режима не создавай. Для обязательного режима объяснение равно `null`, и нужен хотя бы один случай.

Не создавай визуальные метрики для случая без эталона. Значения `viewport.width` и `viewport.height` заданы в CSS-пикселях, а `viewport.dpr` задаёт масштаб устройства. Для захвата всей области `logicalDimensions` равно `null`: логический размер берётся из области просмотра. Для селектора и полной страницы с эталоном укажи измеренные логические размеры. `pixelRounding` (`floor`, `ceil` или `round`) задаёт перевод произведения логического размера и DPR в целые пиксели; без эталона оба поля равны `null`. Перед каждой проверкой получи фактические `window.innerWidth`, `window.innerHeight` и `window.devicePixelRatio` и сопоставь их с контрактом.

Запускай проектный захват только по проверенному контракту и выбранному случаю. Возьми точный шаблон `provisioning.visualCaptureCommand`, один раз замени `{caseId}` на `caseId` выбранного случая и выполни получившуюся команду из корня Git-репозитория. Не добавляй и не переставляй аргументы.

Для сравнения возьми точный `provisioning.visualCompareCommand`, один раз замени `{caseId}` и `{iteration}` на выбранный случай и номер итерации из трёх цифр. Получившаяся команда получает снятый интерфейс и неизменяемый эталон, создаёт машиночитаемый результат и не меняет эталон.

После `G4` значение `<implementation-id>` равно 64 шестнадцатеричным знакам `implementationHash` без префикса `sha256:`. Ниже каталог `artifacts/visual/<task-id>/implementations/<implementation-id>/` обозначен как `<version-root>`. Все хешируемые результаты `G4`-`G7` храни там неизменяемо. Корневой `implementation-manifest.json` указывает на текущую реализацию и совпадает со своей копией в этом каталоге.

## Публичная проверка полного прохода

Для завершения используй один поддерживаемый публичный интерфейс из runtime-скилла:

```bash
node <skill-root>/scripts/verify-all.mjs <task-id> [--project-root <path>]
```

Без `--project-root` команда использует текущий каталог потребительского проекта. Она по `<task-id>` сама находит `artifacts/visual/<task-id>/`, проверяет текущий последовательный проход `G0`–`G8` по [переходам журнала](./gates.md) и печатает один из стабильных результатов:

- `VERIFY_ALL_PASS gate=G8 task=<task-id>` и код `0` — все гейты закрыты.
- `VERIFY_ALL_CONTRACT_FAILURE gate=<G*> evidence=<path> ...` и код `1` — остановись на первом незакрытом гейте и исправь названное свидетельство.
- `VERIFY_ALL_ENVIRONMENT_FAILURE reason=<id> ...` и код `2` — исправь вызов или среду потребительского проекта и повтори команду.

`verify-all` — единственное свидетельство завершения. Он запускает профильные валидаторы внутри публичного интерфейса; отдельный успешный запуск валидатора полезен только для диагностики и не закрывает гейт сам по себе.

Для `task-contract.json` v2 перед дописыванием события `G8` используй тот же интерфейс с `--preflight-g8`. При успехе он печатает ровно одну JSON-строку готового события; допиши её в журнал одной операцией и немедленно повтори обычный `verify-all`. Для v1 доступна только итоговая проверка полного прохода.

## Структурированная готовность

Поле `readiness` принимает только `url-equals`, `selector-visible`, `selector-hidden`, `text-present`, `fonts-ready`, `images-ready`. Исполнитель выбирает встроенную проверку по `kind`; контракт не содержит и не передаёт JavaScript.

В каждом случае должны быть ровно по одной записи `url-equals`, `fonts-ready` и `images-ready`. Для `url-equals` используй точный канонический адрес, полученный из `target.origin` и `route`; другой origin запрещён. `selector` оставь равным `null`. Для проверок селектора используй значение из `selectors`; только `text-present` также получает `expected`, которое должно входить в `selectors.dynamicText`. Захват селектора требует `selector-visible` для того же селектора; захват всей области или полной страницы — хотя бы один `selector-visible` из объявленных селекторов. Для `fonts-ready` и `images-ready` оба поля равны `null`. Встроенная проверка шрифтов использует фиксированное условие `document.fonts?.status === 'loaded'`. Проверка изображений требует `complete && naturalWidth > 0` для каждого изображения. Эти условия задаёт процедура, а не контракт. Неизвестный вид проверки вызывает `STOP` до захвата.

## Браузер и доступность

Перед работой выполни `agent-browser skills get core --full` и следуй [процедуре CLI](../references/agent-browser-cli.md). Для источника и реализации используй разные сессии `source` и `candidate`. Все параметры бери из текущего случая; не подставляй значения, которых нет в контракте.

Сохрани `console` и `errors` до действий, очисти буферы и повтори чтение после действий. Любая новая ошибка означает, что проверка не пройдена. После смены состояния или размера снова проверь URL, готовность, фактический размер, DPR и селекторы.

Проверь управление клавиатурой, порядок и видимость фокуса, доступные имена, контраст, порядок чтения, переполнение, перенос содержимого и работу при увеличении масштаба. Для случая `behavior-only` JSON содержит утверждения `keyboard`, `focus`, `accessible-name`, `contrast`. Для `responsive-only` обязательны `overflow`, `reading-order`, `reflow`, `zoom`. Эти значения записываются в `assertions[*].kind` дословно; каждое утверждение содержит конкретные `expected`, `actual` и `status: "passed"`.

## Случаи без эталона

Для `behavior-only` и `responsive-only` создай `artifacts/visual/<task-id>/<case-id>/evidence.json` по [шаблону](../templates/browser-evidence.json). Он содержит текущий `implementationHash`, `captureContractHash` — SHA-256 точных байтов канонического `capture-contract.json`, все данные, однозначно определяющие случай, непустые `actions` и все четыре обязательных вида `assertions` для своего режима, пустые `consoleErrors` и `pageErrors`, а также `status: "passed"`.

Сохрани побайтно равную копию в `artifacts/visual/<task-id>/implementations/<implementation-id>/cases/<case-id>/evidence.json`. Корневой файл относится к текущей реализации, копия сохраняет историю. Каталог корневого случая содержит только `evidence.json`; не создавай там PNG, `iterations`, `raw.json`, `result.json`, долю различий или тестовую копию эталона.

## Проверки Q1-Q6 и проекта

На `G5` выполни по порядку:

1. `Q1`: теги, роли, заголовки, подписи и иерархия DOM.
2. `Q2`: совместимые компоненты проекта и обоснование новых границ.
3. `Q3`: состояния, взаимодействия, клавиатура, фокус, доступное имя и контраст.
4. `Q4`: каждая пара обязательного состояния и области просмотра, длинное содержимое, переполнение, порядок чтения, перенос и увеличение масштаба.

Сохрани результаты `Q1`-`Q6` как `<version-root>/checks/q1.md` и далее. На `G6` выполни все `acceptance.projectChecks` в точном порядке, на `G7` так же выполни `acceptance.browserChecks`, затем `Q5` и `Q6`.

Файл `<version-root>/checks/<id>.txt` для команды начинается с одной строки JSON с полями `schemaVersion: 1`, точной `command`, фактическим `exitCode`, а также числом байтов `stdoutBytes` и `stderrBytes`. После LF без разделителей идут точные байты stdout, затем stderr. Поэтому корректная команда без вывода всё равно оставляет проверяемую запись. В `verification-record.json` проверка получает `status: "passed"` только при `exitCode: 0`; заголовок, размеры потоков, путь и SHA-256 должны совпасть с сохранённым файлом.

## Проверка средства сравнения

Если контракт содержит хотя бы один случай `visual-reference`, на `G7` до сравнения интерфейса создай каноническую пару RGBA PNG размером 2 на 2: эталон содержит четыре чёрных пикселя, второй файл отличается одним белым пикселем. Проектная команда сравнения должна вернуть `differentPixels: 1`, `totalPixels: 4`, `differenceRatio: 25`.

Сохрани `comparator-conformance.json` в `<version-root>`, а входы, `raw.json`, `diff.png` и `overlay.png` в `<version-root>/conformance/`, используя [шаблон](../templates/comparator-conformance.json). Запись содержит текущие `taskId` и `implementationHash`. Значения `profile: "rgba-exact-v1"`, `pixelThreshold: 0`, `antialiasPolicy: "count"` и канонические пути должны совпасть со схемой. В `artifactHashes` события `G7` укажи запись и все пять файлов из `conformance/`. Несоответствие делает последующие визуальные результаты недействительными.

## Неизменяемая визуальная итерация

Каждый случай `visual-reference` хранит эталон и каталоги `001`, `002` и далее без пропусков:

```text
artifacts/visual/<task-id>/<case-id>/reference.png
artifacts/visual/<task-id>/<case-id>/iterations/<NNN>/
  actual.png
  reference.png
  diff.png
  overlay.png
  raw.json
  analysis.md
  result.json
```

Набор содержит ровно эти семь файлов и не меняется после записи. `reference.png` в корне случая, в итерации и в `tests/visual/references/figma/<task-id>/<case-id>.png` совпадают побайтно.

Перед присвоением номера новой итерации проверь URL, готовность, состояние, фактический размер, DPR, среду и `Q1`-`Q4`. Сбой до сравнения запиши по [шаблону сбоя](../templates/failure-record.json) как `failures/<sequence из четырёх цифр>-<case-id>.json`, затем добавь `failed-pre-diff` без `iteration`: `evidencePath` указывает на эту запись, и только она входит в `artifactHashes`. Исправление закрывает сбой только для того же случая. После полного набора добавь `iteration-completed`: номера одного случая строго растут, а в `artifactHashes` входят ровно семь файлов в порядке шаблона и, при принятом ненулевом остатке, запись ручного одобрения последним элементом. `raw.json` и `result.json` содержат `implementationHash` реализации, для которой создана итерация, и текущий `captureContractHash`. Только последняя итерация каждого случая обязана использовать текущий `implementationHash`.

По профилю `rgba-exact-v1` сравнивай 8-битные sRGB RGBA без изменения размера. Пиксель отличается при несовпадении любого байта; порог каналов равен `0`, сглаживание учитывается. Разные размеры останавливают сравнение. Формула не округляется:

```text
differenceRatio = differentPixels / totalPixels * 100
```

Числовой результат принимается только при `success: true`, `error: null`, `dimensionMismatch: null`, конечном и согласованном `differenceRatio`. В `raw.json` также запиши `referenceChecksum`, `actualChecksum`, `diffChecksum` и `overlayChecksum`. Эти поля должны совпасть с SHA-256 соответствующих файлов итерации. Допуск проверки равен `Number.EPSILON * max(1, abs(calculated)) * 8`.

Значение `pixel-perfect` допустимо только при точном нуле и без `mismatch`; поле `approval` равно `null`. Статус `strict-visual-accepted` допустим при `0 < differenceRatio <= 15`, если остались только подтверждённые `micro` различия в категориях `geometry`, `spacing`, `typography`, `colors` или `borders and shadows`. Для такого результата человек создаёт запись по [шаблону](../templates/visual-approval.json) в `<version-root>/approvals/<case-id>-<NNN>.json`. Она называет ответственного и причину, содержит хеши `raw.json` и `analysis.md`, а `result.json.approval` — путь и хеш самой записи. Событие итерации также включает этот хеш. Остальные случаи получают `failed` и `approval: null`.

## Анализ восьми категорий

Создай `analysis.md` по [шаблону](../templates/visual-analysis.md) после `raw.json`. Таблица имеет заголовок `Category | Status | Evidence | Diagnosis | Disposition` и категории в таком порядке: `geometry`, `spacing`, `typography`, `colors`, `borders and shadows`, `assets`, `responsive behavior`, `missing or extra elements`.

Для `match` значение `Disposition` равно `accepted: no action`. Для `not-applicable` используй `not applicable: no action`. Каждый `mismatch` содержит `Issue refs: N` только в `Evidence`, конкретные `expected` и `actual`, а также ровно один уровень: `macro` или `micro`. Для обычного `mismatch` укажи `next fix: ...`; для принятого мелкого остатка вместо него используй `accepted micro residual: ...`. Категории `assets`, `responsive behavior`, `missing or extra elements` не допускают остатков.

Каждой проблеме из `result.json.issues` соответствует ровно один номер `Issue refs:`, и каждый номер указывает ровно на одну проблему. Нумеруй проблемы сначала по порядку категорий, а внутри каждой категории по порядку элементов в DOM.

## Канонические записи и команды

Корень задачи хранит общие документы и указатели:

```text
artifacts/visual/<task-id>/compatibility.md
artifacts/visual/<task-id>/task-contract.json
artifacts/visual/<task-id>/capture-contract.json
artifacts/visual/<task-id>/design-context-manifest.json
artifacts/visual/<task-id>/source-manifest.json
artifacts/visual/<task-id>/pre-code-evidence.md
artifacts/visual/<task-id>/implementation-manifest.json
artifacts/visual/<task-id>/verification-record.json
artifacts/visual/<task-id>/final-report.md
artifacts/visual/<task-id>/evidence-log.jsonl
```

Подтверждения каждой реализации хранятся отдельно:

```text
artifacts/visual/<task-id>/implementations/<implementation-id>/implementation-manifest.json
artifacts/visual/<task-id>/implementations/<implementation-id>/checks/
artifacts/visual/<task-id>/implementations/<implementation-id>/cases/<case-id>/evidence.json
artifacts/visual/<task-id>/implementations/<implementation-id>/approvals/
artifacts/visual/<task-id>/implementations/<implementation-id>/comparator-conformance.json
artifacts/visual/<task-id>/implementations/<implementation-id>/conformance/
```

Корневые `evidence.json`, эталоны и визуальные итерации находятся в каталогах случаев. Их содержимое связывается с версией через `implementationHash` и журнал.

Из точного корня Git-репозитория проекта запускай публичную проверку по фактическому пути установленного пакета. Профильные валидаторы допустимо запускать отдельно только для диагностики: отдельный результат не закрывает ни один гейт.

После успешного `G7` подготовь `verification-record.json` и предварительную версию `final-report.md`, затем для контракта v2 запроси событие `G8`:

```bash
node <skill-root>/scripts/verify-all.mjs <task-id> \
  --project-root . \
  --preflight-g8
```

Предварительная проверка ничего не записывает. Она принимает только журнал, в котором `G7` закрыт, а событие `G8` ещё отсутствует, виртуально добавляет успешное событие и проверяет оба итоговых файла. При успехе код равен `0`, а стандартный вывод содержит ровно готовую JSON-строку. При нарушении контракта код равен `1`, при ошибке входа или среды код равен `2`; вывод ошибки нельзя добавлять в журнал.

После кода `0` не меняй журнал и хешированные файлы. Одной операцией допиши напечатанную строку в `evidence-log.jsonl`, затем сразу повтори публичный вызов без `--preflight-g8`. Он обязан вернуть `VERIFY_ALL_PASS gate=G8 task=<task-id>` и код `0`; только после этого работа завершена. На время этих трёх действий исключи параллельные записи.

## Итоговая запись и отчёт

На `G8` создай корневой `verification-record.json` по [шаблону](../templates/verification-record.json). Его `implementationHash` совпадает с текущим `rootHash`. `qualityChecks` содержит `Q1`-`Q6` по порядку и ссылается на `<version-root>/checks/q1.md` и далее. `projectChecks` и `browserChecks` дословно повторяют `id` и `command` из задачи, а их `outputPath` имеет вид `<version-root>/checks/<id>.txt`. У каждой записи есть `status: "passed"`, `exitCode: 0` и SHA-256 сохранённого результата.

Заполни [`final-report.md`](../templates/final-report.md) из проверенных артефактов. До дописывания выданного события это предварительная версия: записи о пройденном `G8` становятся действительными вместе с успешным событием в журнале. Таблицы запросов, источников, файлов реализации, зависимостей, проверок, случаев и сбоев переносятся из канонических JSON и журнала без добавлений. Строки областей просмотра выводи из `$.viewports`, строки состояний из `$.states`; пути подтверждений бери из соответствующих случаев контракта захвата. В столбец `issues` переноси точный массив из итогового `result.json`, преобразованный по правилам шаблона, а в `approval` — `null` либо точные путь и хеш ручного одобрения. Сохраняй порядок элементов и связь полей каждой проблемы.

Свободный текст разрешён только в полях, прямо помеченных как ручные: изменениях модели, прочих согласованных отклонениях, не заменяющих `approval` визуальной итерации, и оставшихся допущениях. Валидатор проверяет их наличие и отсутствие подсказок шаблона, но не истинность; проверяющий человек сопоставляет их с указанными материалами.

Отсутствующий, неканонический, устаревший, неверно хешированный файл или файл, являющийся символической ссылкой, не проходит проверку. Рекурсивная опись двух каталогов задачи допускает только файлы, объявленные каноническими записями и событиями; лишний, специальный или нечитаемый файл также останавливает процесс. То же относится к неполной матрице, лишнему полю, неверной идентичности, неполному журналу и итоговому подтверждению текущего прохода с прежним `implementationHash`. Исторические итерации сохраняют исходный хеш. При ошибке примени `STOP` и назови первый открытый этап. После сохранения диагностики закрой сессии браузера.

## Граница автоматической проверки

Валидаторы проверяют схемы, идентичность, пути, хеши, полноту матрицы, точные пиксельные метрики, согласованность записей и неизменяемые копии. Без доверенного исполнителя или подписи они не доказывают, кто вызвал Figma и браузер, что команда действительно запускалась в заявленной среде и что ручное заключение верно. Запись принятого остатка связывает решение с точной итерацией, но не удостоверяет личность ответственного. Семантику DOM, доступность, уместность повторного использования компонентов и классификацию различий проверяет человек по сохранённым материалам. Работай в закрытом рабочем каталоге: проверка путей не защищает от другого процесса, который меняет файл между чтениями.
