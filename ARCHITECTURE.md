# Архитектурный контракт

Статус: принят для развития стартера. Основа: vertical slice с правилом зависимостей
clean architecture, адаптированные к Next.js App Router.

Этот файл фиксирует решения проекта. [OpenWiki](openwiki/architecture/overview.md) объясняет
их применение и связывает с реализацией. Код и конфигурация определяют фактическое поведение;
расхождение с контрактом требует исправления или явного пересмотра решения.

## Функциональность начинается рядом с маршрутом

Vertical slice объединяет код одного пользовательского сценария: UI, входные данные,
правила и обращение к внешнему API. Тесты и stories принадлежат тому же сценарию,
но физически находятся в отдельных зеркальных деревьях. Например, просмотр каталога
и редактирование товара являются разными сценариями. URL сам по себе не определяет
границу бизнес-логики.

Для одного маршрута сценарий остаётся в `app/.../`. `page.tsx` и `layout.tsx` собирают
страницу, локальный UI находится в единственной `_components/`. Остальные файлы лежат
рядом с маршрутом. Если несколько локальных сценариев разрастаются, объединяйте их
логику в приватные каталоги с именем сценария, сохраняя UI в `_components/`.

`src/modules/<capability>/` появляется, когда одна бизнес-возможность нужна минимум двум
маршрутам. Внутри модуля код группируется по сценариям, например `list-products/` и
`edit-product/`. Только действительно общие для этих сценариев правила поднимаются
на уровень модуля. Не переносите бизнес-логику в `src/utils/` ради второго потребителя.

Модули не импортируют друг друга. Их совместную работу собирает маршрут, layout или
явная функция композиции в `app/`, передавая данные и зависимости. Общий provider
не становится владельцем бизнес-сценариев.

## Направление зависимостей внутри сценария

Clean architecture отделяет правила продукта от способов их выполнения. Направление
импортов определяется ответственностью файла, а не только его расположением в `app/`
или `src/`.

| Часть       | Ответственность                                                     | Разрешённые зависимости                                                  |
| ----------- | ------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| Domain      | Инварианты и вычисления предметной области                          | Собственные типы, чистые функции без framework и IO                      |
| Application | Выполнение сценария, порядок шагов, ожидаемые результаты и порты IO | Domain и объявленные в сценарии интерфейсы зависимостей                  |
| Adapters    | SDK, преобразование DTO, чтение env, URL, cookies, cache API        | Application, domain, публичные API facets и нужная инфраструктура        |
| UI          | Отображение, форма, пользовательские события                        | Общий UI, безопасные типы и чистые правила сценария, клиентские адаптеры |
| Composition | Соединение конкретных адаптеров со сценарием и Next.js              | Все необходимые части в подходящей среде выполнения                      |

Domain и application не импортируют React, Next.js, TanStack Query, env, logger,
`#/api` или generated типы. Порт принадлежит сценарию и описывает нужную ему операцию,
а не весь backend. Конкретный адаптер реализует этот контракт. Зависимости передаются
обычными аргументами функций; контейнер внедрения зависимостей не нужен.

Поток вызовов может идти из use case во внешний API через переданную функцию. Это
не меняет направление импортов: use case знает только собственный порт, а адаптер
знает порт и SDK. DTO преобразуется в доменную модель только при различии смыслов
или формы данных. Не создавайте копии generated типов и схем без такой причины.

`domain/`, `application/` и `adapters/` являются необязательными каталогами. Для
небольшого сценария достаточно нескольких соседних файлов с понятными именами.
Чистая функция правила не требует класса, базового repository или общего use-case API.

## Простой экран и сценарий с правилами

Экран, который только отображает ответ API, может вызвать публичный SDK из Server
Component или использовать `#/api/query` в клиентском компоненте. Его компонент
совмещает отображение с тонким адаптером; отдельный application слой здесь не нужен.

Когда появляется правило продукта, последовательность операций или независимая
политика ошибок, вынесите их из компонента в чистую функцию или use case. Например,
расчёт доступного количества относится к domain, а проверка результата и сохранение
изменённого заказа через переданный порт относятся к application. HTTP-статусы,
`redirect`, `notFound`, `revalidatePath` и `QueryClient` остаются в адаптерах.

Бизнес-ошибка является ожидаемым типизированным результатом сценария. UI переводит
её в сообщение или состояние поля. Ошибки рендера обрабатывает граница ошибки.
Ошибки submit, event handlers и асинхронных мутаций обрабатывайте явно в вызывающем
адаптере: error boundary не перехватывает их автоматически. Логирование выполняется
в адаптере через `#/observability/logger`. Ошибки не заменяются пустым успешным результатом.

## Размещение и публичные импорты

| Код                                                         | Место                                                       |
| ----------------------------------------------------------- | ----------------------------------------------------------- |
| Сборка страницы, metadata, loading/error, HTTP endpoint     | `app/`                                                      |
| UI одного маршрута                                          | `app/.../_components/`                                      |
| Схемы формы, правила и адаптеры одного маршрута             | Рядом с маршрутом                                           |
| Бизнес-возможность минимум двух маршрутов                   | `src/modules/<capability>/`                                 |
| UI без знания бизнес-сущностей                              | `src/components/ui/<component>/`                            |
| Инфраструктурный provider                                   | `src/components/providers/`                                 |
| Контракт backend, SDK, Zod, Query options, Faker, transport | `src/api/`                                                  |
| Настройки и общая инфраструктура                            | Существующие `src/env/`, `src/proxy/`, `src/observability/` |

Общий код `src/*` вне `src/modules/` не импортирует маршруты и доменные модули.
UI-примитивы не импортируют API, env или бизнес-сущности. Общие `hooks`, `utils`
и `types` содержат только код без знания конкретного сценария.

Внешний потребитель импортирует публичный `index.ts` или `index.tsx`. Если модуль
имеет серверную и клиентскую части, он предоставляет отдельные точки входа
`server.ts` и `client.ts`; общий index содержит только универсальные экспорты.
Не реэкспортируйте серверный адаптер через клиентский barrel.

Алиасы сохраняются: `@/*` для `app/`, `#/*` для `src/`, `~/*` для корня.
Общий UI импортируется через `#/components/ui/<component>`. API импортируется через
`#/api`, `#/api/client`, `#/api/query`, `#/api/schemas`, `#/api/mocks` и
`#/api/cache-tags`. `src/api/codegen/` остаётся внутренней структурой генератора.

## Граница Next.js и браузера

Server Component используется по умолчанию. `'use client'` задаёт вход в клиентский
граф импортов; ставьте его на интерактивный компонент, которому нужны state,
effects, события или browser API. Client Component может участвовать в серверном
рендеринге HTML, поэтому browser API нельзя безусловно читать при его рендеринге.

Переданный через `children` Server Component не становится клиентским из-за provider.
Через серверную границу передаются минимальные сериализуемые React данные, без
секретов и объектов зависимостей. Обычные callback-функции через неё не проходят;
Server Function передаётся как специальная ссылка Next.js.

Суффиксы `.server.ts` и `.client.ts` обозначают намерение, но сами не защищают
импорт. Новые серверные адаптеры с секретами защищайте `import 'server-only'`.
Чистые domain/application функции остаются универсальными. Не помечайте use case
директивой `'use server'`: удалённая Server Action является отдельным входным адаптером.

В текущей инфраструктуре `src/api/client-config.ts` универсален и импортирует
`serverEnvironment`, читая его только в серверной ветке. В `src/env/server.ts` нет
маркера `server-only`; доступ к серверным значениям защищает env-библиотека во время
выполнения. Это существующая граница транспорта, а не образец для импорта env в UI.
Клиентские компоненты используют только `clientEnvironment` из `src/env/client.ts`.

Server Actions и Route Handlers проверяют входные параметры. Защищённые операции
при каждом вызове проверяют аутентификацию и право на конкретное действие; webhook
проверяет подлинность отправителя. Клиентская валидация формы и скрытая кнопка
не заменяют серверные проверки. В стартере готового слоя авторизации нет.

## Загрузка, мутации и владение состоянием

Серверный адаптер обращается к backend через SDK напрямую. Не добавляйте HTTP-запрос
из Server Component в собственный Route Handler только для вызова той же функции.
Route Handler нужен при отдельном HTTP-контракте, например для webhook или BFF-операции.

Текущий transport выбирает `BACK_INTERNAL_URL` на сервере, `NEXT_PUBLIC_BFF_PATH`
в development-браузере и `NEXT_PUBLIC_BACK_URL` в production-браузере. Server Action
не обязательна для каждого запроса. Для защищённой серверной операции она может
стать адаптером, но её наличие не превращает весь browser API в BFF.

| Состояние                                                 | Владелец                                       |
| --------------------------------------------------------- | ---------------------------------------------- |
| Результат серверного чтения                               | Server Component и явно выбранная cache policy |
| Данные API для интерактивного браузерного сценария        | TanStack Query                                 |
| Фильтр, сортировка, пагинация, которыми делятся через URL | URL и nuqs                                     |
| Значения, ошибки и отправка формы                         | `useAppForm` из общего UI                      |
| Локальное раскрытие, выделение, временное UI-состояние    | React state или reducer                        |

Next server cache и Query cache независимы. Мутация обновляет или инвалидирует
каждый затронутый кеш явно. `use cache`, cache tags, lifetime и `Suspense` относятся
к серверному адаптеру, а не к domain/application. Request-specific данные нельзя
помещать в общий кеш без корректной изоляции. Действуют
[правила Cache Components](openwiki/architecture/cache-and-streaming.md).

Не дублируйте серверные данные в глобальном React store. Глобальный provider
добавляется только для глобальной задачи; состояние отдельного сценария остаётся
внутри его маршрута или компонента.

## Проверки границ

Unit-тесты находятся в `tests/unit/`, компонентные в `tests/component/`, stories
в `stories/src/components/` и только для компонентов из `src/components/`. Для `app/` stories запрещены. После префикса тестов каталог повторяет путь исходника от корня,
включая `app/` или `src/`. Тесты и stories рядом с исходниками запрещены.
Например, `src/components/ui/button/button.tsx` соответствует
`tests/component/src/components/ui/button/button.component.test.tsx` и
`stories/src/components/ui/button/button.stories.tsx`.

Чистые правила и use cases проверяются в unit project в Node. Для IO use case
получает небольшой подставной порт. SDK-адаптеры используют существующие generated
схемы, Faker и mock client. Vitest выбирает `tests/unit/**/*.test.{ts,tsx}` и
`tests/component/**/*.test.{ts,tsx}`; component project работает в Chromium.
`src/tests/` содержит общую инфраструктуру, fixtures, mocks и Playwright E2E.

Для нового компонента `.tsx` в `src/components/` или `app/**/_components/` нужны
тест с тем же базовым именем; story требуется только для `src/components/`. `index.tsx` с реализацией тоже является
компонентом; чистый re-export исключён. Интерактивность проверяется component test.
При переносе исходника переносите его тесты и stories в соответствующие зеркальные пути.

Приоритет оформления принадлежит Tailwind и существующим tokens. CSS Modules
допустимы только в `src/styles/`, вне маршрутов и каталогов компонентов.
`npm run check:structure` проверяет размещение, зеркальные пути, наличие тестов и
stories у компонентов и ограничения CSS Modules. Проверка включена в `verify:fast`
и pre-commit. Все компоненты в проверяемых каталогах имеют тест, а компоненты
из `src/components/` также имеют story; исключений нет.
Для произвольного теста скрипт проверяет
директорию исходника; одноимённость проверяется отдельно для обязательного теста
компонента. Проверка наличия файлов не доказывает качество тестов и пока не охватывает
компоненты будущего `src/modules/`.

Значимый маршрут проверяется E2E через вход пользователя, включая ошибки и мутации.
Для нового route/config/env/proxy
нужен production build; production E2E запускается после свежей сборки с
`PLAYWRIGHT_SERVER_MODE=standalone`. Список команд находится в
[руководстве по тестированию](openwiki/testing/testing.md).

`npm run check:imports` проверяет граф локальных импортов из `app/` и `src/` до lint
и TypeScript в `verify:fast`, поэтому проверка выполняется и pre-commit. Скрипт разбирает
AST через Oxc: обычные и type-only imports, реэкспорты, `import()` и `require()`.
Пути разрешаются по `paths` корневого tsconfig и относительным путям, включая index
и замену расширений JS на TS. Вычисляемые пути и неразрешённые локальные импорты запрещены.

Проверяются shared → app/modules, module → app/другой module, UI → API/env/modules,
публичные входы API, модулей и компонентов, а также чужой route-local `_components/`.
Запреты слоёв учитывают транзитивные зависимости через локальные helpers и barrels.
Исходники `src/tests/` и generated API не получают собственных архитектурных ограничений,
но их зависимости участвуют в графе; runtime не импортирует тестовую инфраструктуру.

Чистый слой распознаётся по каталогу `domain/` или `application/`. Для плоской структуры
поместите первой строкой файла `/** @architecture domain */` или
`/** @architecture application */`. Маркер обязателен для чистых правил и use cases,
расположенных вне каталогов слоёв. Это сохраняет возможность обходиться без пустых каталогов.
Проверка запрещает им framework/Node IO imports, инфраструктуру проекта и адаптеры;
`domain` также не зависит от `application`. Неотмеченный файл нельзя автоматически
распознать как бизнес-правило, поэтому правильность классификации проверяется при ревью.

Проверка анализирует зависимости, а не выполнение кода: обращения к глобальным browser API,
семантика функции, авторизация, секреты и RSC-сериализация требуют отдельных проверок.
Содержимое сторонних npm-пакетов не обходится. Она не заменяет Next build и правила RSC
в Oxlint. Конфигурация путей читается из JSON tsconfig без наследования `extends`.

## Текущее состояние и развитие

В стартере есть главная страница с локальным `Hero`, общие UI/providers, API-клиент,
моки, env, proxy и observability. `src/modules/`, бизнес-use-cases и продуктовые
Server Actions пока отсутствуют. Petstore демонстрирует API-генерацию; он не является
реализованным продуктовым модулем. Runtime fixture в `src/tests/fixtures/api-runtime/`
не является маршрутом приложения.

Новые слои вводятся вместе с использующим их сценарием. Не создавайте пустые каталоги,
глобальные `domain/`, `application/`, `repositories/` или второй набор `features/entities`
поверх этого размещения. Изменение контракта сопровождается обновлением `AGENTS.md`,
примеров применения в OpenWiki и затронутых проверок.

Правила Next.js сверены с установленными руководствами `node_modules/next/dist/docs/`
и официальной документацией:

- [Организация проекта](https://nextjs.org/docs/app/getting-started/project-structure).
- [Server и Client Components](https://nextjs.org/docs/app/getting-started/server-and-client-components).
- [Безопасность данных](https://nextjs.org/docs/app/guides/data-security).
- [Backend for Frontend](https://nextjs.org/docs/app/guides/backend-for-frontend).
